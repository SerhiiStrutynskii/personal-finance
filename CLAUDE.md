# CLAUDE.md — Household Finance App

Правила для AI-асистента в цьому репозиторії. Тримай файл коротким і актуальним:
якщо AI двічі робить ту саму помилку — додай правило сюди.

## Про проект

Веб-застосунок для обліку фінансів домогосподарства: витрати, доходи, борги, бюджети,
цілі накопичення. Аналітика, індикація перевитрат, поради щодо оптимізації витрат,
виходу з боргів і накопичення капіталу.

## Стек

- Backend: Node.js + TypeScript, Express 5
- Frontend: React + TypeScript, Vite, React Query, Tailwind, shadcn/ui, Recharts (графіки, через shadcn `chart`)
  (компоненти в apps/web/src/shared/ui; нові додавати через `npx shadcn@latest add <name>` в apps/web)
- БД: PostgreSQL, ORM/міграції: Drizzle (drizzle-kit, міграції в apps/api/drizzle)
- Авторизація: власна — JWT (jose) + refresh-токени з ротацією, паролі argon2id
- Тести: Vitest (unit, зокрема логіка фронтенду без UI), Supertest (API, окрема база TEST_DATABASE_URL), Playwright (e2e)

## Структура

```
apps/api        — бекенд (src/modules/<feature>/{routes,service,repo,schema,tests})
apps/web        — фронтенд (src/features/<feature>/...)
packages/shared — спільні типи, zod-схеми, утиліти для грошей і дат
docs/           — domain.md, api.md, decisions/ (ADR)
```

## Команди

```
npm run dev          # запуск усього локально
npm run build        # зібрати фронтенд (apps/web/dist)
npm run start        # продакшн: міграції + API; розгортання — docs/deploy.md
npm run test         # усі тести
npm run test:e2e     # Playwright; сам піднімає API і фронтенд на тестовій базі (порти 3100 і 5174)
npm run lint         # eslint + prettier
npm run typecheck    # tsc --noEmit
npm run db:generate  # згенерувати міграцію зі змін у apps/api/src/db/schema.ts
npm run db:migrate   # застосувати міграції
npm run db:seed      # тестові (фейкові) дані
```

Перед тим як вважати задачу виконаною: `lint`, `typecheck`, `test` мають проходити.

## Доменна модель (коротко; деталі в docs/domain.md)

User, Household (кілька користувачів), Account (картка, готівка, депозит),
Transaction (income | expense | transfer), Category, Budget (ліміт на категорію/період),
Debt (сума, ставка, мінімальний платіж, графік), Goal (ціль накопичення),
Product (довідник продуктів із ціною за одиницю для списків покупок).

## Критичні правила

### Гроші

- НІКОЛИ не використовувати float для сум. У БД — `BIGINT` у мінімальних одиницях (копійки)
  або `NUMERIC(14,2)`; у коді — ціле число копійок або decimal-бібліотека.
- Кожна сума має валюту (ISO 4217, за замовчуванням UAH). Не складати суми різних валют
  без явної конвертації.
- Переказ між рахунками — це не витрата і не дохід; він не впливає на аналітику витрат.
- Усі фінансові розрахунки (баланси, бюджети, борги, відсотки) — тільки з unit-тестами,
  включно з граничними випадками.

### Дати

- Зберігати `timestamptz` в UTC; групування по днях/місяцях — у часовому поясі користувача.
- Періоди бюджету: початок включно, кінець виключно.

### Безпека і дані

- Кожен запит до даних фільтрується за householdId поточного користувача.
  Перевірка доступу — в сервісному шарі, а не тільки на фронті.
- Валідація всіх вхідних даних через zod-схеми з packages/shared.
- Паролі — тільки argon2/bcrypt. Не логувати токени, паролі, суми з персональними даними.
- Не додавати нові залежності без погодження.
- Не змінювати вже застосовані міграції — тільки нові.
- Не використовувати реальні фінансові дані в тестах, сидах чи промптах.

### Поради та аналітика

- Розрахунки (перевитрата, прогноз, стратегії погашення боргів: avalanche/snowball) —
  детерміновані функції з тестами, окремо від UI.
- Тексти порад не мають звучати як професійна фінансова/інвестиційна консультація.

## Як працювати

1. Задача більша за ~30 рядків → спочатку план (файли, міграції, API, тести), чекати погодження.
2. Одна фіча = вертикальний зріз: міграція → repo → service → route → тести → UI.
3. Маленькі коміти, Conventional Commits (`feat:`, `fix:`, `refactor:`...).
4. Якщо змінюється API — оновити docs/api.md і спільні типи.
5. Не вигадувати поведінку, якої немає в docs — запитати.
