# Місячний бюджет

Перед роботою прочитай CLAUDE.md (правила щодо грошей, дат і доступу до даних), docs/domain.md
і скіл `incomes` (звідки беруться доходи).

## 1. Що робить фіча

Бюджет — це **план лімітів витрат по категоріях на місяць** плюс зведення фактичних даних за цей місяць.
Сам бюджет фактичних записів не зберігає:

- **Доходи** беруться з фічі доходів (скіл `incomes`) за період бюджету. На екрані бюджету доходи
  тільки показуються. Додавання, отримання й редагування доходів відбувається на сторінці «Доходи».
- **Фактичні витрати** беруться з видатків (`Transaction`, `type = expense`) за період бюджету
  і групуються за їхньою категорією. На рядках категорій витрати не додаються.
- **Ліміти** — єдине, що вводиться в самому бюджеті: запланована сума на кожну категорію.

На екрані бюджету є кнопка «+ Видаток», яка відкриває **ту саму модалку, що й на сторінці видатків**.
Створений видаток автоматично потрапляє у відповідну категорію бюджету, бо належить до періоду за датою.

Видаток можна додати на сьогодні або будь-яку минулу дату, але не на майбутню (див. розділ 4).
З екрана бюджету видатки додаються лише в поточному періоді; заднім числом — зі сторінки видатків.

Стан кожної категорії:
- **червоний** — фактичні витрати перевищили ліміт (одразу, в будь-який момент періоду);
- **зелений** — період завершився, і по категорії лишився залишок;
- **нейтральний** — усі інші випадки.

## 2. Доменна модель

### Budget
- `id`, `householdId`, `periodStart` (перше число місяця, 00:00 у таймзоні household),
  `periodEnd` (перше число наступного місяця, виключно), `currency`, `createdAt`, `updatedAt`.
- Один бюджет на household на місяць (унікальний індекс `householdId + periodStart`).
- Стан періоду не зберігається, а обчислюється відносно поточного моменту:
  - `past` — `now >= periodEnd`;
  - `current` — `periodStart <= now < periodEnd`;
  - `future` — `now < periodStart`.

### BudgetExpenseLine — ліміт по категорії
- `id`, `budgetId`, `categoryId`, `plannedAmount` (копійки, >= 0), `sortOrder`.
- Унікально `budgetId + categoryId`.

### Що бюджет НЕ зберігає
- Статей доходу немає. Запланований і фактичний дохід місяця бере сервіс доходів.
- Фактичних витрат немає. Їх рахує агрегація по `transactions`.

Видаток належить до бюджету за датою `occurredAt ∈ [periodStart, periodEnd)` і householdId,
а не через звʼязок з budgetId.

У `spent` ідуть транзакції двох типів (див. скіл `debts`, розділ 5):
- `expense` — звичайні видатки, зокрема покупки, відсотки й комісії з кредитної картки;
- `debt_payment` — платежі по позиках і розстрочках, у системній категорії «Погашення боргів».

Не враховуються: перекази між рахунками (`transfer`, зокрема погашення кредитки — її покупки
вже пораховані) і службові зміни балансу (`balance_adjustment`).

## 3. Розрахунки (чисті функції в packages/shared/budget)

Усі суми — цілі числа в копійках.

Для кожної категорії витрат:
```
planned   = expenseLine.plannedAmount (0, якщо ліміту немає)
spent     = сума expense- і debt_payment-транзакцій категорії з occurredAt у періоді
remaining = planned - spent          // може бути відʼємним
usage     = planned > 0 ? spent / planned : (spent > 0 ? ∞ : 0)
```

Статус категорії `getCategoryStatus(planned, spent, now, periodEnd)`:
```
if spent > planned                           → "over"     (червоний)
else if now >= periodEnd && spent < planned  → "surplus"  (зелений)
else                                         → "neutral"
```
Правила:
- `spent == planned` — це `neutral`, навіть після завершення періоду (рівно в межах).
- Витрати в категорії без ліміту вважаються з `planned = 0`, тому дають `over`.
  В UI такі категорії показуються окремим блоком «Незаплановані витрати».
- Статус обчислює бекенд і повертає в API. Фронтенд колір не вираховує, а лише мапить статус на стиль.

Доходи — з сервісу доходів (`incomes`), без власної логіки в бюджеті:
```
plannedIncomeTotal  = incomes.summary.plannedTotal   за період бюджету
receivedIncomeTotal = incomes.summary.receivedTotal  за період бюджету
```
Сервіс бюджету викликає сервіс доходів, а не дублює його SQL чи розрахунки.

Підсумок бюджету:
```
plannedIncomeTotal, receivedIncomeTotal,
plannedExpenseTotal = сума лімітів,
spentTotal          = сума всіх видатків за період (включно з незапланованими),
plannedBalance = plannedIncomeTotal - plannedExpenseTotal
actualBalance  = receivedIncomeTotal - spentTotal
```
Якщо `plannedExpenseTotal > plannedIncomeTotal`, показується попередження, але збереження не блокується.

## 4. Обмеження за періодом

### Видатки
Правило діє в API створення/редагування видатків для всього застосунку,
а не лише на екрані бюджету, бо модалка і endpoint спільні.

- Створити видаток можна з будь-якою датою `occurredAt <= now`, зокрема в минулих періодах.
  Майбутня дата заборонена.
- Видатки минулих періодів можна редагувати й видаляти; дату видатку можна перенести в інший
  період, але не в майбутнє.
- Порушення → `422` з кодом `EXPENSE_DATE_IN_FUTURE`. Перевірка робиться на бекенді;
  фронтенд лише обмежує вибір дати, щоб помилка не виникала.

### Ліміти
- `current` і `future` — ліміти можна додавати, змінювати й видаляти.
- `past` — бюджет лише для читання.
- Створити бюджет можна для поточного або майбутнього місяця.
- Новий бюджет (без `copyFrom`) одразу отримує ліміт «Погашення боргів» на суму щомісячних платежів
  активних позик і розстрочок, якщо вони є. Кредитки в цю суму не входять.

## 5. API

```
GET    /budgets?month=2026-10              → бюджет із розрахунками, доходами та periodState (або 404)
POST   /budgets                            { month, copyFrom?: "2026-09" } → створити (копіюються лише ліміти)
POST   /budgets/:id/expense-lines          { categoryId, plannedAmount }
PATCH  /budgets/:id/expense-lines/:lineId  { plannedAmount?, sortOrder? }
DELETE /budgets/:id/expense-lines/:lineId
```
Видатки створюються через той самий endpoint, що й на сторінці видатків (`POST /transactions`
з `type = expense`). Окремого endpoint-у для видатків з бюджету немає.

Приклад відповіді `GET /budgets?month=2026-10`:
```json
{
  "id": "...", "month": "2026-10", "periodState": "current", "currency": "UAH",
  "canAddExpense": true, "canEditLimits": true,
  "summary": { "plannedIncomeTotal": 6000000, "receivedIncomeTotal": 5250000,
               "plannedExpenseTotal": 5200000, "spentTotal": 3180000,
               "plannedBalance": 800000, "actualBalance": 2070000 },
  "incomes": {
    "occurrences": [
      { "name": "Зарплата", "plannedDate": "2026-10-05", "plannedAmount": 4500000,
        "actualAmount": 4500000, "status": "received" },
      { "name": "Аванс", "plannedDate": "2026-10-15", "plannedAmount": 1500000,
        "actualAmount": 0, "status": "pending" }
    ],
    "oneTimeTotal": 750000
  },
  "expenseLines": [{ "id": "...", "categoryId": "...", "categoryName": "Продукти",
                     "planned": 1200000, "spent": 1350000, "remaining": -150000,
                     "usage": 1.125, "status": "over" }],
  "unplannedExpenses": [{ "categoryId": "...", "categoryName": "Подарунки", "spent": 80000, "status": "over" }]
}
```
`canAddExpense` і `canEditLimits` обчислює бекенд з `periodState`. Фронтенд на них орієнтується,
але не замінює ними перевірку в API.

Правила:
- Кожен запит перевіряє, що бюджет належить household поточного користувача.
- Вхідні дані валідуються zod-схемами з packages/shared.
- Зміна лімітів у бюджеті `past` → `409`.

## 6. База даних (міграція)

```sql
CREATE TABLE budgets (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  household_id uuid NOT NULL REFERENCES households(id) ON DELETE CASCADE,
  period_start timestamptz NOT NULL,
  period_end   timestamptz NOT NULL,
  currency char(3) NOT NULL DEFAULT 'UAH',
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (household_id, period_start),
  CHECK (period_end > period_start)
);

CREATE TABLE budget_expense_lines (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  budget_id uuid NOT NULL REFERENCES budgets(id) ON DELETE CASCADE,
  category_id uuid NOT NULL REFERENCES categories(id),
  planned_amount bigint NOT NULL CHECK (planned_amount >= 0),
  sort_order int NOT NULL DEFAULT 0,
  UNIQUE (budget_id, category_id)
);

-- індекс для агрегації: transactions (household_id, type, occurred_at, category_id)
```
Агрегація `spent` по категоріях — один SQL-запит з `GROUP BY category_id`, а не цикл у коді.
Таблиць для доходів у бюджеті немає.

## 7. UI (apps/web/src/features/budget)

Екран «Бюджет на місяць»:
- перемикач місяця (← жовтень 2026 →); якщо бюджету немає (поточний або майбутній місяць) —
  кнопки «Створити» та «Скопіювати ліміти з попереднього»;
- картка підсумку: план/факт доходів, план/факт витрат, залишок;
- блок «Доходи» — лише перегляд: надходження з індикаторами статусу (як у скілі `incomes`),
  сума разових доходів, посилання «Перейти до доходів». Кнопок додавання доходу тут немає;
- блок «Витрати»: рядок на категорію з лімітом, прогрес-баром `spent / planned`, залишком і статусом.
  Ліміт редагується інлайн (якщо `canEditLimits`). Кнопок додавання витрат у рядках немає;
- блок «Незаплановані витрати» (якщо є) з дією «Додати ліміт»;
- кнопка «+ Видаток» у шапці екрана, лише якщо `canAddExpense`.

Модалка видатку:
- використовується **той самий компонент**, що й на сторінці видатків
  (наприклад, `features/expenses/components/ExpenseFormModal`). Не створюй копію в features/budget;
- приймає пропси `minDate` / `maxDate`; дата за замовчуванням — сьогодні, майбутні дати недоступні.
  На екрані бюджету вибір додатково обмежений поточним періодом (`minDate` — перше число місяця),
  щоб видаток потрапив у бюджет, з якого його додали; на сторінці видатків нижньої межі немає;
- обмеження дат береться з однієї спільної функції в packages/shared (`getAllowedExpenseDateRange`),
  яку використовують і фронтенд, і бекенд;
- після збереження інвалідуються запити бюджету, видатків і аналітики (React Query).

Стилі статусів:
- `over` — червоний фон/бордер рядка + іконка ⚠ + текст «Перевищено на X ₴»;
- `surplus` — зелений + іконка ✓ + текст «Залишок X ₴»;
- `neutral` — звичайний вигляд.
Колір ніколи не є єдиним індикатором: завжди є іконка й текст (доступність).
Кольори беруться з токенів теми (`--status-over`, `--status-surplus`) з підтримкою темної теми.

Для минулого місяця екран лише для читання: немає кнопки «+ Видаток» і редагування лімітів.

## 8. Тести (обовʼязкові)

Unit (`getCategoryStatus`, розрахунки):
- spent < planned, період триває → neutral
- spent < planned, період завершився → surplus
- spent == planned, період завершився → neutral
- spent > planned на 1 копійку → over (і під час, і після періоду)
- planned = 0, spent > 0 → over; planned = 0, spent = 0 → neutral
- now рівно = periodEnd → період вважається завершеним
- перекази не впливають на spent
- платіж по позиці (`debt_payment`) входить у spent; `balance_adjustment` — ні

Unit (`getAllowedExpenseDateRange`, `getPeriodState`):
- 1-ше число 00:00 за Києвом — поточний період; 31-ше 23:59 — ще поточний; 1-ше наступного — вже новий
- дата минулого місяця чи року дозволена
- майбутня дата недоступна, навіть у межах поточного місяця

API (Supertest):
- видаток з датою минулого місяця → 201
- видаток з майбутньою датою → 422 `EXPENSE_DATE_IN_FUTURE`
- редагування/видалення видатку минулого місяця дозволені
- видаток поточного місяця в категорії з лімітом зʼявляється в `spent` цієї категорії
- видаток у категорії без ліміту зʼявляється в `unplannedExpenses`
- доходи в бюджеті збігаються з `GET /incomes?month=...` за той самий місяць
- зміна лімітів у минулому бюджеті → 409
- створення бюджету для минулого місяця → 422
- чужий бюджет → 404; дубль бюджету на місяць → 409
- копіювання з попереднього місяця переносить лише ліміти

E2E (Playwright): відкрити бюджет поточного місяця → «+ Видаток» → видаток понад ліміт категорії →
рядок червоний, підсумок оновився. Відкрити минулий місяць → кнопки «+ Видаток» немає.

## 9. Порядок реалізації

1. Чисті функції: статуси, `getPeriodState`, `getAllowedExpenseDateRange`, підсумок + unit-тести.
2. Обмеження дат у API видатків (спільне для всього застосунку) + тести.
3. Міграція бюджетів і лімітів.
4. Repo + service + routes бюджету (з викликом сервісу доходів) + API-тести.
5. Перевикористання `ExpenseFormModal` з пропсами `minDate` / `maxDate`.
6. UI: підсумок → витрати зі статусами → блок доходів (перегляд) → копіювання лімітів.
7. E2E, оновлення docs/api.md і docs/domain.md.

Кожен крок — окремий коміт. Перед кроком 4 покажи план endpoint-ів і чекай погодження.

## 10. Поза межами цієї фічі (не реалізовувати без окремої задачі)
- перенесення залишку категорії на наступний місяць (rollover);
- попередження при наближенні до ліміту (наприклад, 80%);
- бюджети не на календарний місяць (з дня зарплати);
- мультивалютні бюджети;
- додавання чи редагування доходів з екрана бюджету.
